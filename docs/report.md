## Цель работы

Научиться составлять тест-кейсы для готового кода, проверять граничные значения
и ошибки входных данных, писать и запускать автотесты на pytest.

## 1. Анализ исходного кода

Для работы взял функцию `cost_bounds` из проекта GameForge, файл
`src/prompt2play/pricing.py`. Она рассчитывает стоимость использования модели
по количеству входных и выходных токенов. Часть готовых тестов также взята
из GameForge, из файлов `test_pricing.py` и `test_financial_ledger.py`.
Саму функцию перенёс в [pricing.py](../pricing.py) без изменений.

У функции два аргумента: `usage` с количеством токенов и `pricing` с тарифами.
Она возвращает кортеж из двух чисел — минимальную и максимальную оценку
стоимости. Разница между ними появляется, если неизвестно число записанных
в кеш токенов или статистика содержит несколько запросов сразу.

Результат выражен в нанодолларах: 1 доллар равен 1 000 000 000 нанодолларов.
Для расчётов используется `Decimal`, результат округляется вверх до целого числа.

### Входные данные

| Параметр | Что означает | Допустимые значения |
| --- | --- | --- |
| `input_tokens` | Общее число входных токенов | Целое число от 0 |
| `cached_input_tokens` | Входные токены, прочитанные из кеша | Целое число от 0 до `input_tokens` |
| `output_tokens` | Число выходных токенов | Целое число от 0 |
| `cache_write_tokens` | Число входных токенов, записанных в кеш | От 0 до `input_tokens - cached_input_tokens`; поле может отсутствовать или быть `None` |
| `usd_per_million` | Цены за миллион токенов: обычный вход, чтение кеша, запись кеша и выход | Четыре тарифа, в тестах записаны десятичными строками |
| `long_context_threshold` | Порог длинного запроса | В тестах 272 000 токенов |
| `long_input_multiplier`, `long_output_multiplier` | Повышающие коэффициенты для длинного запроса | В тестах 2 и 1,5 |
| `provider` | Способ учёта запросов | В тестах `openai` или `codex` |

Отрицательные значения, строки, дробные числа, `bool` и `None` в обязательных
счётчиках вызывают `ValueError`. Для `cache_write_tokens` значение `None`
допускается и означает, что число записей неизвестно.

### Бизнес-правила

1. Поля `input_tokens`, `cached_input_tokens` и `output_tokens` обязательны.
   Они должны содержать неотрицательные целые числа. `True` и `False` не принимаются.
2. Кешированные токены уже входят в общее количество входных. Поэтому их
   должно быть не больше, чем `input_tokens`.
3. Число записей в кеш не должно превышать число входных токенов, которые
   не были прочитаны из кеша.
4. Обычный вход, чтение кеша, запись кеша и выход считаются по разным тарифам.
5. Если число записей неизвестно, нижняя оценка считает оставшийся вход
   обычным, а верхняя — записанным в кеш.
6. Повышенный тариф действует при входе больше 272 000 токенов.
   На самой границе ещё используется обычный тариф.
7. Для `openai` известен размер одного запроса, поэтому повышающий коэффициент
   применяется к обеим оценкам. Для `codex` статистика может объединять несколько
   запросов, поэтому нижняя оценка остаётся по обычному тарифу, а верхняя — по повышенному.
8. При нулевом расходе стоимость равна нулю. Два отдельных коротких запроса
   рассчитываются отдельно, даже если их суммарный размер превышает порог.
9. Обе оценки округляются вверх до целого нанодоллара. Входные словари не изменяются.

### Классы эквивалентности и границы

| Что проверяется | Классы и граничные значения |
| --- | --- |
| Обязательные счётчики | Отрицательное число, ноль, положительное число, неверный тип, отсутствующее поле |
| Кешированный вход | Нет кеша; часть входа; весь вход; кеш больше общего входа |
| Записи в кеш | Неизвестны; меньше нуля; ноль; часть оставшегося входа; весь остаток; превышение остатка |
| Длина запроса | 271 999, 272 000 и 272 001 токен |
| Округление | Целая стоимость и дробная стоимость меньше или больше одного нанодоллара |

## 2. Тест-кейсы

Перед запуском нужно установить зависимости и импортировать функцию из
`pricing.py`. Каждый тест получает свой набор тарифов, поэтому изменения
в одном тесте не влияют на остальные.

В таблицах использованы следующие наборы тарифов:

| Набор | Обычный вход | Чтение кеша | Запись кеша | Выход |
| --- | ---: | ---: | ---: | ---: |
| A — основной | 10 | 1 | 12,50 | 50 |
| B — малый тариф | 0,10 | 0,01 | 0,125 | 0,50 |
| C — другой тариф из GameForge | 2 | 0,10 | 2,50 | 10 |
| R — для округления | 0,0004 | 0,0001 | 0,0011 | 0,005 |

Цены указаны в долларах за миллион токенов. Это фиксированные данные для
тестов. По умолчанию используются набор A и `provider = openai`.

Вход записан как `(I, C, O; W)`: общее число входных токенов, чтение кеша,
выход и запись в кеш. Знак `—` означает, что поле записи не передано.
Ожидаемая стоимость указана в нанодолларах.

Например, для TC-01 получаем:

```text
Нижняя оценка: (10000 × 10 + 90000 × 1 + 1000 × 50) × 1000 = 240000000
Верхняя оценка: (10000 × 12,5 + 90000 × 1 + 1000 × 50) × 1000 = 265000000
```

Множитель 1000 переводит цену за миллион токенов в нанодоллары за токен.

Шаги обычного теста: передать данные в функцию и сравнить полученный кортеж
с ожидаемым. В тестах на ошибки проверяются тип исключения и его сообщение.
После вызова исходные словари должны остаться без изменений.

## 3. Реализация и запуск тестов

Тесты находятся в [tests/test_pricing.py](../tests/test_pricing.py).
Для похожих проверок используется `pytest.mark.parametrize`: одни и те же
действия выполняются с разными входными данными. Поэтому 31 тест-кейс из
таблицы даёт 50 отдельных проверок.

Из готовых тестов оставлены проверки кеша, нулевого расхода, порога длинного
запроса, отдельных запросов и точного числа записей в кеш. Добавлены проверки
типов, пропущенных полей, допустимых границ записи, округления и сохранности
входных данных.

Запуск выполнялся на Python 3.14.7 с pytest 9.1.1:

```bash
pytest -v
```

Результат:

```text
collected 50 items
50 passed in 0.03s
```

Полный вывод сохранён в [pytest.txt](results/pytest.txt).

Дополнительно проверено покрытие с помощью coverage 7.16.2:

## 4. Вывод

В работе составлен 31 тест-кейс и выполнено 50 автоматических проверок.
Все тесты прошли. Проверены обычный расчёт, работа с кешем, переход на
повышенный тариф, округление и обработка неверных входных данных.
Coverage показал 100% покрытия строк и учитываемых им ветвей модуля.

Остались ограничения: функция рассчитывает стоимость по уже подготовленным
тарифам, а сами тарифы здесь не проверяются. Также не проверялись очень большие
счётчики и взаимодействие с внешним сервисом. Поэтому полное покрытие строк
ещё не означает, что проверены все возможные ситуации.

Тесты помогают находить ошибки при разработке и проверять, что изменения
не сломали готовый расчёт. Например, при изменении тарифов или правил кеша
можно повторно запустить этот набор и сравнить результаты с ожидаемыми.
Поэтому тестирование нужно как при создании программы, так и при её дальнейшем сопровождении.
