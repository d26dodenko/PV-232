## Часть 1. Теоретическая

### 1.1. Основные проблемы разработки сложных программных систем

**Управление сложностью.** По мере роста программы увеличивается количество модулей и связей между ними. Изменение одного компонента может повлиять на несколько других. Это затрудняет поиск ошибок и увеличивает трудоёмкость сопровождения. Разделение программы на модули с определёнными обязанностями позволяет проверять и изменять их по отдельности.

**Неполные и изменяющиеся требования.** Неоднозначное описание функции допускает несколько вариантов реализации. Разработчик и пользователь могут по-разному понимать ожидаемый результат. Требования нужно уточнять через конкретные сценарии, а изменения согласовывать до доработки кода. Для проверки корректности каждому требованию задают критерий приёмки.

**Обеспечение надёжности.** Ошибки могут проявляться только при определённом порядке действий, на границах допустимых значений или при взаимодействии компонентов. После изменения кода ранее работающий сценарий может перестать выполняться. Автоматические тесты позволяют повторять такие проверки, а анализ покрытия помогает найти непроверенные участки.

### 1.2. Проблемы, решения и инструменты

| Проблема | Возможное решение | Инструменты и методы |
|---|---|---|
| Рост сложности и связности | Разделить обязанности модулей, сократить функции с большим числом ветвлений | Модульная архитектура, ревью кода, цикломатическая сложность, Radon |
| Неоднозначные и меняющиеся требования | Описать сценарии использования и критерии приёмки, фиксировать изменения | Трекер задач, прототипирование, приёмочные тесты |
| Ошибки и регрессии | Проверять обычные, ошибочные и граничные случаи после изменений | Модульное и интеграционное тестирование, pytest, coverage.py |

## Часть 2. Практическая

### 2.1. Создание проекта на Python

Разработана игра «Морской бой» на Python с интерфейсом Pygame. Игрок сражается с компьютером на двух полях размером 10 × 10 клеток. Флот каждой стороны состоит из одного четырёхпалубного, двух трёхпалубных, трёх двухпалубных и четырёх однопалубных кораблей.

При запуске корабли расставляются автоматически с зазором между ними, включая диагонали. Игрок ходит первым. Попадание сохраняет ход, промах передаёт его сопернику. Повторный выстрел по клетке игнорируется. Компьютер выбирает случайную необстрелянную клетку. Побеждает сторона, потопившая весь флот противника.

| Действие | Управление |
|---|---|
| Выстрел | Левая кнопка мыши по клетке правого поля |
| Новая партия | Кнопка «Новая партия» или клавиша R |
| Выход | Esc или закрытие окна |

![Окно игры «Морской бой»](docs/game.png)

*Рисунок 1 — собственный флот и результаты выстрелов по противнику.*

Структура проекта отражает разделение игровой логики и интерфейса.


В Windows окружение создаётся командой `py -3.12 -m venv .venv` и активируется в PowerShell командой `.\.venv\Scripts\Activate.ps1`. Установка зависимостей и запуск игры выполняются теми же двумя последними командами.

### 2.7. Цикломатическая сложность

Для расчёта выбран метод `Board.fire`, который проверяет выстрел и определяет его результат.

```python
def fire(self, cell: Cell) -> Shot | None:
    """Вернуть результат нового выстрела. Недопустимый ход ничего не меняет."""
    if cell not in CELLS or cell in self.shots:
        return None
    ship = self.ship_at.get(cell)
    if ship is None:
        self.shots[cell] = Shot.MISS
        return Shot.MISS

    self.shots[cell] = Shot.HIT
    if ship <= self.shots.keys():
        self.shots.update(dict.fromkeys(ship, Shot.SUNK))
        self.afloat -= 1
    return self.shots[cell]
```

В методе три оператора `if`. Логический оператор `or` в первой проверке добавляет ещё одну точку ветвления. С учётом базового пути получаем **V(G) = 1 + 3 + 1 = 5**.

```sh
python -m radon cc -s battleship/board.py
```

Radon подтверждает результат — **`Board.fire - A (5)`**. [Исходный код метода](battleship/board.py)
