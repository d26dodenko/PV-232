Документация: https://restful-booker.herokuapp.com/apidoc/index.html

Структура коллекции `LabAPI_Zubarev` (8 запросов, 3 папки по ресурсам):

### 3.2. Баг-репорты

Во всех баг-репортах ниже «валидное тело» означает следующий JSON, в котором меняется только указанное поле:

```json
{
  "firstname": "Ivan",
  "lastname": "Petrov",
  "totalprice": 100,
  "depositpaid": true,
  "bookingdates": {
    "checkin": "2026-11-10",
    "checkout": "2026-11-15"
  },
  "additionalneeds": "Breakfast"
}
```

Заголовки для POST/PUT/PATCH: `Content-Type: application/json`, `Accept: application/json`. Для PUT/PATCH/DELETE
дополнительно `Cookie: token=<token>`, токен получают запросом `POST /auth` с `admin` / `password123`.

#### BUG-01. DELETE `/booking/{id}` возвращает 201 Created

- **Шаги:**
    1. Выполнить `POST /auth`, получить `token`.
    2. Выполнить `POST /booking` с валидным телом, получить `bookingid`.
    3. Выполнить `DELETE /booking/{bookingid}` с заголовком `Cookie: token=<token>`.
- **Ожидаемый результат:** 200 OK или 204 No Content.
- **Фактический результат:** 201 Created, тело ответа `Created`.
- **Серьёзность:** низкая (Minor). Функционально удаление работает, нарушена семантика кодов HTTP, клиенты,
  ориентирующиеся на стандарт, могут обрабатывать ответ неверно.

#### BUG-02. GET `/ping` возвращает 201 Created

- **Шаги:** выполнить `GET /ping`.
- **Ожидаемый результат:** 200 OK.
- **Фактический результат:** 201 Created, тело ответа `Created`.
- **Серьёзность:** низкая (Minor). Мониторинг, проверяющий код 200, будет считать сервис недоступным.

#### BUG-03. POST `/auth` с неверными учётными данными возвращает 200 OK

- **Шаги:**
    1. Выполнить `POST /auth` с телом `{"username": "admin", "password": "wrong"}`.
    2. Повторить с телом `{"username": "wrong", "password": "password123"}`.
- **Ожидаемый результат:** 401 Unauthorized.
- **Фактический результат:** 200 OK, тело `Bad credentials` (TC-N01, TC-N02).
- **Серьёзность:** средняя (Major). Ошибка аутентификации сообщается кодом успеха, клиент вынужден разбирать тело
  ответа; автоматические проверки по коду статуса пропускают ошибку.

#### BUG-04. 405 Method Not Allowed вместо 404 для отсутствующего ресурса

- **Шаги (вариант A):**
    1. Создать бронирование и удалить его (`POST /booking`, затем `DELETE /booking/{id}` с токеном).
    2. Выполнить `GET /booking/{id}` для удалённого `id`.
- **Шаги (вариант B):** выполнить `DELETE /booking/{id}` с токеном для несуществующего `id`.
- **Ожидаемый результат:** 404 Not Found.
- **Фактический результат:** 405 Method Not Allowed (TC-P09, TC-N07). При этом `GET /booking/99999999` для никогда не
  существовавшего `id` возвращает корректный 404 (TC-N06), то есть поведение непоследовательно.
- **Серьёзность:** низкая (Minor). Код вводит в заблуждение: метод поддерживается, проблема в отсутствии ресурса.

#### BUG-05. PUT/PATCH/DELETE без токена или с некорректным токеном возвращают 404

- **Шаги:**
    1. Выполнить `PUT /booking/{id}` с валидным телом без заголовка `Cookie`.
    2. Выполнить `PATCH /booking/{id}` с телом `{"firstname": "Test"}` и `Cookie: token=invalid`.
    3. Выполнить `DELETE /booking/{id}` без заголовка `Cookie`.
- **Ожидаемый результат:** 401 Unauthorized или 403 Forbidden.
- **Фактический результат:** 404 Not Found, тело `Not Found` (TC-N03, TC-N04, TC-N05). При этом PUT с неполным
  JSON (TC-N12) вернул 403 Forbidden, то есть реакция на отсутствие авторизации нестабильна.
- **Серьёзность:** средняя (Major). Вместо отказа в доступе клиент получает «ресурс не найден».
- **Примечание:** результат получен при использовании `id`, который мог быть уже удалён. Для окончательного вывода
  повторить шаги с `id` существующего бронирования.

#### BUG-06. POST `/booking` с неполными данными возвращает 500 Internal Server Error

- **Шаги:**
    1. Выполнить `POST /booking` с валидным телом без поля `firstname`.
    2. Выполнить `POST /booking` с пустым телом.
- **Ожидаемый результат:** 400 Bad Request с описанием ошибки валидации.
- **Фактический результат:** 500 Internal Server Error, тело `Internal Server Error` (TC-N10, TC-N11).
- **Серьёзность:** средняя (Major). Ошибка клиента обрабатывается как ошибка сервера, нет валидации обязательных
  полей. При этом некорректный JSON даёт корректный 400 (TC-N08).

#### BUG-07. POST `/booking` принимает строку в `totalprice` и сохраняет `null`

- **Шаги:** выполнить `POST /booking` с валидным телом, в котором `"totalprice": "abc"`.
- **Ожидаемый результат:** 400 Bad Request.
- **Фактический результат:** 200 OK, в теле ответа `"totalprice": null` (TC-N09).
- **Серьёзность:** высокая (Critical для учебной оценки качества данных). Нет проверки типа, невалидное значение молча
  заменяется на `null`, искажается финансовое поле.

#### BUG-08. POST `/booking` принимает пустые `firstname` и `lastname`

- **Шаги:** выполнить `POST /booking` с валидным телом, в котором `"firstname": ""` и `"lastname": ""`.
- **Ожидаемый результат:** 400 Bad Request.
- **Фактический результат:** 200 OK, бронирование создано (TC-B01).
- **Серьёзность:** низкая (Minor). Нет проверки обязательных строковых полей на пустое значение.

#### BUG-09. POST `/booking` принимает отрицательный `totalprice`

- **Шаги:** выполнить `POST /booking` с валидным телом, в котором `"totalprice": -100`.
- **Ожидаемый результат:** 400 Bad Request.
- **Фактический результат:** 200 OK, бронирование создано (TC-B04).
- **Серьёзность:** средняя (Major). Нет проверки диапазона, допускается отрицательная стоимость.

#### BUG-10. POST `/booking` принимает `checkout` раньше `checkin`

- **Шаги:** выполнить `POST /booking` с валидным телом, в котором `"checkin": "2026-11-15"`,
  `"checkout": "2026-11-10"`.
- **Ожидаемый результат:** 400 Bad Request.
- **Фактический результат:** 200 OK, бронирование создано (TC-B06).
- **Серьёзность:** средняя (Major). Нет проверки логической согласованности дат.

#### BUG-11. POST `/booking` принимает невалидный формат даты и сохраняет повреждённое значение

- **Шаги:** выполнить `POST /booking` с валидным телом, в котором `"checkin": "31-31-2026"`.
- **Ожидаемый результат:** 400 Bad Request.
- **Фактический результат:** 200 OK, в теле ответа `"checkin": "0NaN-aN-aN"` (TC-B07).
- **Серьёзность:** высокая (Critical для учебной оценки качества данных). Нет проверки формата даты, в хранилище
  попадает

покрыты все 8 эндпоинтов, настроена автоматическая передача `token` и `bookingId` между запросами. Полный прогон в

укладывается в порог 2000 мс.

Сравнение с принятыми REST-практиками выявило нестандартное поведение API: DELETE и `/ping` возвращают 201 Created. Это
не мешает работе сервиса, но нарушает семантику HTTP-кодов, поэтому такие случаи оформлены как особенности API низкой
серьёзности. Для надёжной клиентской интеграции необходимо опираться на фактическое поведение, а не на ожидания по
стандарту.

Автоматические проверки статуса, структуры ответа и времени ответа позволяют повторно запускать сценарий после любых
изменений сервиса и быстро находить регрессии.
