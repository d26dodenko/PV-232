# Отчёт по лабораторной работе

**Тема:** Критерии качества ПО: сложность, корректность, надёжность, трудоёмкость. Оценка качества ПО.

**Цель:** Освоить практические методы оценки качества и метрик программного обеспечения.

---

## 1. Три наиболее значимые проблемы при разработке сложных программных систем

### 1.1. Управление сложностью системы

Сложная программная система состоит из сотен и тысяч модулей, десятков подсистем и множества связей между ними. Ф. Брукс
в работе «Серебряной пули нет» выделяет *существенную* сложность ПО: она определяется самой решаемой задачей и не
устраняется средствами разработки. Количество возможных состояний системы растёт нелинейно, поэтому:

- ни один разработчик не способен удерживать в голове систему целиком;
- растёт число скрытых зависимостей, и изменение в одном месте неожиданно ломает другое;
- затрудняются понимание кода, его сопровождение и вхождение новых людей в проект;
- растут метрики сложности (цикломатическая сложность, связность модулей), а вместе с ними и вероятность дефектов.

Следствие: архитектура «размывается», накапливается технический долг, а трудоёмкость сопровождения растёт быстрее, чем
размер кодовой базы.

### 1.2. Неполные и изменчивые требования

Требования к крупной системе почти никогда не фиксируются полностью в начале проекта. Заказчик часто не может точно
сформулировать, что ему нужно, пока не увидит работающий прототип; бизнес-условия, законодательство и технологии
меняются во время разработки. Основные последствия:

- доработки на поздних этапах стоят в разы дороже, чем исправление ошибок на этапе анализа;
- расхождение между ожиданиями заказчика и реализацией (низкая *корректность* в смысле соответствия требованиям);
- срыв сроков и бюджета, «ползучее» расширение объёма (scope creep);
- противоречия между функциональными и нефункциональными требованиями (производительность, безопасность, удобство).

### 1.3. Обеспечение качества, корректности и надёжности

Доказать корректность сложной системы формально, как правило, невозможно, а полное тестирование недостижимо из-за
комбинаторного взрыва входных данных и состояний. Поэтому в готовом ПО неизбежно остаются дефекты. Дополнительные
сложности:

- ошибки, обнаруженные поздно (в эксплуатации), обходятся дороже всего;
- трудно воспроизводимые дефекты: гонки потоков, сбои интеграции, зависимость от окружения;
- необходимость обеспечивать надёжность (отказоустойчивость, среднее время наработки на отказ) при постоянных изменениях
  кода;
- сложность оценки трудоёмкости и сроков тестирования и исправления дефектов.

## 4. Практическая часть

### 4.1. Тестовый проект

В качестве объекта исследования создан консольный калькулятор на Python 3. Проект небольшой, но содержит ветвления,
обработку ошибок и несколько уровней вызовов, поэтому на нём удобно показать работу метрик.

**Структура проекта:**

```
calculator_project/
├── calculator/
│   ├── __init__.py
│   ├── operations.py     # базовые операции и функция classify_number
│   ├── calculator.py     # класс Calculator: разбор выражений, история
│   └── cli.py            # консольный интерфейс
├── tests/
│   ├── test_operations.py
│   ├── test_calculator.py
│   └── test_cli.py
├── main.py
└── requirements.txt
```

**Функциональность:**

- операции: сложение, вычитание, умножение, деление, остаток от деления, возведение в степень, квадратный корень,
  процент от числа;
- вычисление выражений со скобками, приоритетом операций и унарными знаками, например `2 + 3 * (4 - 1)`;
- история вычислений (просмотр и очистка);
- консольный интерфейс с командами `help`, `history`, `clear`, `exit`;
- обработка ошибочных ситуаций: деление на ноль, корень из отрицательного числа, некорректное выражение.

**Проектные решения, влияющие на качество:**

- выражения разбираются через модуль `ast`, а не через `eval()`, поэтому выполнить произвольный код через ввод
  невозможно (защита от инъекций);
- логика отделена от ввода-вывода: функция `process_command` и цикл `run` принимают функции ввода и вывода как
  параметры, что позволяет тестировать интерфейс без реального ввода с клавиатуры;
- все ошибки пользователя обрабатываются явно и выводятся как сообщения, а не как падение программы.

#### Ручной расчёт для функции `classify_number`

```python
def classify_number(x):
    if x > 0:
        return "Positive"
    elif x == 0:
        return "Zero"
    else:
        return "Negative"
```

*Через количество условий:* условий два (`x > 0` и `x == 0`), поэтому

$$V(G) = 2 + 1 = 3.$$

*Через граф потока управления.* Узлы: A — проверка `x > 0`; B — `return "Positive"`; C — проверка `x == 0`; D —
`return "Zero"`; E — `return "Negative"`; X — выход из функции. Рёбра: A→B, A→C, B→X, C→D, C→E, D→X, E→X. Получаем N =
6, E = 7, P = 1:

$$V(G) = E - N + 2P = 7 - 6 + 2 \cdot 1 = 3.$$

Оба способа дают 3, что совпадает с результатом `radon` (`classify_number - A (3)`). Три независимых пути соответствуют
трём тестам (положительное число, ноль, отрицательное число), то есть набор тестов полностью покрывает базисное
множество путей.

#### Проверка расчётов `radon` для других функций

Radon прибавляет единицу к базовому значению за каждое ветвление (`if`, `elif`, `for`, `while`, `except`, тернарный
оператор) и за каждый логический оператор `and` / `or`.

- `power`: два оператора `if`, каждый с условием из двух частей (`and`) — 1 + 2 + 2 = **5**.
- `process_command`: четыре `if` (команды `exit`/`quit`, `help`, `history`, `clear`), один тернарный оператор (
  `... if history else ...`) и один `except` — 1 + 4 + 1 + 1 = **7**.
- `Calculator._eval_node`: пять `if` верхнего уровня и вложенные проверки — тип узла (`Constant`, `BinOp`, `UnaryOp`),
  проверка `op_func is None`, проверка `unary_func is None`, проверка типа константы с оператором `or` — итого **8**.

**Анализ:**

- Сложность проекта низкая: весь код укладывается в ранги A и B, критических функций нет.
- Наиболее сложные места — `_eval_node` (8) и `process_command` (7): они содержат больше всего ветвлений. Для них тестов
