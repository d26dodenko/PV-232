## 1. Тестируемый сервис

Я протестировал публичный сервис бронирований **Restful-Booker**: https://restful-booker.herokuapp.com. Ожидания сверял с [документацией API](https://restful-booker.herokuapp.com/apidoc/index.html).

| Метод | Эндпоинт | Назначение |
|---|---|---|
| POST | `/auth` | Получение токена |
| GET | `/booking` | Список бронирований и фильтры |
| GET | `/booking/{id}` | Получение записи |
| POST | `/booking` | Создание записи |
| PUT | `/booking/{id}` | Полное обновление |
| PATCH | `/booking/{id}` | Частичное обновление |
| DELETE | `/booking/{id}` | Удаление записи |
| GET | `/ping` | Проверка доступности |

## 2. Подготовка и автоматизация

В Postman я создал коллекцию **LabAPI_Прядко** с 52 запросами и папками **Auth**, **Booking**, **Health**. В Booking выделил Positive, Negative и Boundary. Для каждого запроса указал цель, входные данные и ожидаемый результат.

| Переменная окружения | Начальное значение | Использование |
|---|---|---|
| baseUrl | https://restful-booker.herokuapp.com | Адрес сервиса |
| token | Пусто | Сохраняю из успешного ответа POST /auth |
| bookingId | Пусто | Сохраняю из поля bookingid при создании записи |

Токен и ID передаются автоматически через `pm.environment.set()` и `pm.environment.get()`. Для PUT, PATCH и DELETE я использовал `Cookie: token={{token}}`. В негативных запросах без авторизации этот заголовок отсутствует; автоматические cookies отключены.

Общие Tests я разместил в Scripts коллекции: они наследуются каждым запросом. Проверяю HTTP-код, время меньше 2000 мс, отсутствие 5xx, формат и содержимое ответа. Дополнительно проверяю типы полей, сохранение переменных, изменения после PUT/PATCH и удаление. На каждый запрос приходится не менее четырёх проверок. Текстовые ответы обрабатываю без обязательного вызова JSON-парсера.

Базовое бронирование:

```json
{
  "firstname": "Bogdan",
  "lastname": "Pryadko",
  "totalprice": 150,
  "depositpaid": true,
  "bookingdates": {"checkin": "2026-12-10", "checkout": "2026-12-20"},
  "additionalneeds": "Breakfast"
}
```

В PUT я меняю имя и фамилию с уникальным суффиксом, цену на 275, depositpaid на false и пожелания на Dinner. В PATCH меняю только цену на 320 и пожелания на Late checkout; остальные поля должны сохраниться. Строки длиной 1001 символ формирую программно через `'Я'.repeat(1001)`.

## 3. Тест-кейсы

Для успешных запросов я использовал коды из примеров документации: создание возвращает 200, удаление и ping — 201. Для ошибочных запросов точные коды в документации не заданы, поэтому 400/401/403/404/405 в таблице являются моими ожиданиями по HTTP. Разницу с фактическими ответами я разобрал в разделе 4.

**Passed** означает, что прошли все проверки сценария. **Failed** означает расхождение хотя бы одной проверки; это не всегда подтверждённый дефект API.

| № | Запрос | Ожидалось по REST / документации | Получено | Вывод |

**Почему при неверном логине и пароле 200:** сервер сообщает об отказе в теле ответа, а не в статусе. Я проверил отсутствие токена отдельно. В задании прямо требуется фиксировать такие расхождения, поэтому я оставил фактический 200 и не заменял ожидание 401 ради успешного теста. Поскольку код отказа не описан в документации, этот случай я отметил как потенциальный дефект, а не как доказанное нарушение контракта.

## 5. Баг-репорты

### BUG-01. Фильтр checkin исключает равную дату

**Серьёзность:** Medium. **Условие:** создана своя запись с checkin=2026-12-10.

**Шаги:** выполнить P02–P07, затем `GET /booking?checkin=2026-12-10`.

**Ожидалось:** 200, свой ID есть в списке согласно документированному >=. **Получено:** 200, своего ID нет. **Вывод:** условие фильтра не соответствует документации.

### BUG-02. Фильтр checkout работает не по документированному условию

**Серьёзность:** Medium. **Условие:** у своей записи checkout=2026-12-20.

**Шаги:** выполнить GET /booking сначала с checkout=2026-12-19, затем с checkout=2026-12-21; дополнительно проверить P13.

**Ожидалось:** 200; в первом списке свой ID есть, во втором его нет. **Получено:** 200; результаты противоположны, P13 возвращает []. **Вывод:** документированное сравнение >= не выполняется.

### BUG-03. Нечисловая цена сохраняется как null

**Серьёзность:** Medium. **Условие:** остальные поля базового JSON корректны.

**Шаги:** отправить POST /booking с totalprice="not-a-number" (N10), затем получить созданную запись.

**Ожидалось:** ориентир отказа 400; при успехе totalprice обязан иметь тип Number. **Получено:** POST 200 и GET 200, totalprice=null в обоих ответах. **Вывод:** нарушен документированный тип поля. Запись после проверки удалена.

### BUG-04. Невалидная дата сохраняется в повреждённом виде

**Серьёзность:** Medium. **Условие:** остальные поля базового JSON корректны.

**Шаги:** отправить POST /booking с checkin=2026-13-40 (B10), затем получить запись.

**Ожидалось:** ориентир отказа 400; успешный ответ содержит действительную дату. **Получено:** POST 200 и GET 200, checkin=0NaN-aN-aN. **Вывод:** нарушен контракт поля Date. Запись после проверки удалена.
