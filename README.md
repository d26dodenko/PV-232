# Лабораторная работа № 2 по тестированию ПС Чернобровенко Александра. Интеграционное и API-тестирование Restful-Booker

Цель работы — освоить тестирование REST API в Postman. Для этого нужно составить коллекцию запросов к Restful-Booker, написать автоматические проверки и сопоставить фактические ответы сервиса с его документацией. [Задание из ветки main](https://github.com/d26dodenko/PV-232/blob/bb38d870c19d5f2a9365dd053ae4bdd09defeb4c/TestingPS/Laba-2.md)

Restful-Booker — учебный REST API для бронирования отелей. [Документация API](https://restful-booker.herokuapp.com/apidoc/index.html)

[Коллекция Postman](postman/collection.json) · [Окружение](postman/environment.json)

## Тестируемые эндпоинты

| Метод и путь | Назначение | Тесты |
| --- | --- | --- |
| `GET /ping` | Проверить доступность | TC-01 |
| `POST /auth` | Получить токен и проверить отказ в авторизации | TC-02, TC-03 |
| `POST /booking` | Создать бронь и получить её ID | TC-04 |
| `GET /booking` | Найти созданную бронь по фильтру firstname | TC-05 |
| `GET /booking/{id}` | Прочитать бронь, проверить последствия отказов и удаления | TC-06, TC-11, TC-23, TC-25 |
| `PUT /booking/{id}` | Полностью заменить бронь, проверить ошибки и границы | TC-07, TC-12–TC-21, TC-26 |
| `PATCH /booking/{id}` | Изменить одно поле, проверить доступ и выбор формата | TC-08–TC-10, TC-22 |
| `DELETE /booking/{id}` | Удалить созданную бронь по токену | TC-24 |

## Тест-кейсы

В каждом запросе три автоматические проверки. Статус PASS означает, что прошли все три. При статусе FAIL дробь показывает, сколько проверок прошло. Для граничных случаев приняты три правила бронирования. Имя гостя должно быть заполнено, цена должна быть неотрицательной, а дата выезда должна совпадать с датой заезда или следовать за ней. Документация API не задаёт этих ограничений явно.

## Баг-репорты

Предусловия для всех четырёх случаев — токен из TC-02 и бронь из TC-04. Запросы на изменение используют её ID и заголовок `Cookie: token={{token}}`.

| ID | Шаги | Ожидаемый результат | Фактический результат | Серьёзность и влияние |
| --- | --- | --- | --- | --- |
| BR-01 | Выполнить TC-14 с полным телом PUT и `totalprice: "abc"`. | 400, цена должна быть числом. | 200, ответ содержит `totalprice: null`. | Высокая. Клиент получает бронь без числовой стоимости. |
| BR-02 | Выполнить TC-20 с заездом 10 декабря и выездом 9 декабря. | 400 по принятому правилу периода проживания. | 200, обе даты возвращены в обратном порядке. | Средняя. Длительность проживания отрицательна. Требование к порядку дат стоит закрепить в контракте. |
| BR-03 | Выполнить TC-21 с `checkin: "not-a-date"`. | 400, некорректная дата отклонена. | 200, вместо даты получено `0NaN-aN-aN`. | Высокая. Значение нельзя использовать как дату. |
| BR-04 | Создать бронь с пожеланием Breakfast. Выполнить TC-22 с `Accept: image/png` и новым пожеланием After-406. Прочитать бронь через TC-23 с `Accept: application/json`. | 406 и прежнее значение Breakfast. | PATCH вернул 500, GET вернул 200 и After-406. | Высокая. Клиент видит ошибку и может повторить уже выполненную операцию. |

## Вывод

Создание, чтение, полное и частичное обновление, а затем удаление прошли с автоматически полученными токеном и ID. Запросы без токена и с неверным токеном вернули 403 и сохранили прежние данные. При этом сервис принял текстовую цену и некорректную дату. В случае с неподдерживаемым форматом ответа PATCH вернул 500, но последующий GET показал, что пожелания гостя изменились.
