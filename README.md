# Лабораторная работа №1
## Составление тест-кейсов для готового кода. Качество ПО и место тестирования в жизненном цикле

## Цель работы

Сформировать представление о качестве ПО и месте тестирования в жизненном цикле; научиться проектировать тест-кейсы (позитивные, негативные, граничные, по эквивалентным классам) и писать автотесты на Python + pytest.

## Тестируемый модуль

`ParkingFeeService` (`parking_fee.py`) — сервис расчёта стоимости парковки.

**Конфигурация (атрибуты `__init__`, значения по умолчанию):** `free_minutes = 30`, `hourly_rate = 100`, `daily_cap = 1000`, `resident_coefficient = 0.7`, `max_minutes = 1440`.

**Методы:** публичный `calculate_fee(minutes, is_resident=False) -> float`; приватные `_validate`, `_is_free`, `_billable_hours`, `_apply_cap`, `_apply_discount`.

## Анализ модуля

**Входные данные:** `minutes` — целое число, `0 <= minutes <= 1440`; `is_resident` — `bool`. **Выход:** стоимость (`float`) или `ValueError`.

**Бизнес-правила**

1. `minutes < 0` или `minutes > 1440` → `ValueError`.
2. `minutes <= 30` → парковка бесплатна (0.0), в том числе для резидентов.
3. Иначе оплачивается каждый начатый час: `ceil(minutes / 60) * 100`.
4. Стоимость не превышает суточный потолок 1000 (потолок применяется до скидки).
5. Резидентам — скидка 30% (множитель 0.7).

**Эквивалентные классы:** `minutes < 0` (недопустимый) / `[0, 30]` (бесплатно) / `[31, 600]` (платно, потолок не достигнут) / `[601, 1440]` (потолок) / `> 1440` (недопустимый); резидент / не резидент.

**Граничные значения:** -1 / 0; 30 / 31; 60 / 61; 600 / 601; 1440 / 1441.

## Выводы

**Покрытые ветви:** обе проверки в `_validate`; бесплатный период и выход из него; расчёт начатых часов; срабатывание и несрабатывание потолка; скидка для резидентов и её отсутствие; комбинации «бесплатно + резидент» и «потолок + резидент»; настройка тарифов через конструктор.

**Оставшиеся риски:**
- Сообщение об ошибке для верхней границы содержит число 1440, хотя `max_minutes` настраивается: при другом значении текст будет неверным. Тест TC-16 проверяет только тип исключения.
- Типы входных данных не проверяются (`None`, строки, `float`, `bool`).
- Не определено поведение для нескольких суток (более 1440 минут запрещено, а не тарифицируется).
- Правило «любой начатый час оплачивается полностью» даёт скачок: 30 минут — 0, 31 минута — 100.

**Связь качества ПО, тестирования и жизненного цикла.** Качество ПО — это соответствие требованиям и ожиданиям пользователей; в нашем случае — бизнес-правилам тарификации. Тестирование объективно проверяет это соответствие и сообщает о рисках. Чем раньше найден дефект (при проектировании и разработке, а не в эксплуатации), тем дешевле его исправление, поэтому тест-кейсы полезно составлять уже на этапе анализа требований. Автотесты также служат регрессионной защитой: при изменении тарифов (например, потолка или бесплатного порога) они сразу показывают, какое правило нарушено. Кроме того, при проектировании тестов были выявлены неочевидные места в требованиях (граница 30/31 минуты, порядок применения потолка и скидки) — это пример того, как тестирование улучшает качество ещё до запуска продукта.
